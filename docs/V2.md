# NetPresence v2: proximity-graph attendance

## 1. Idea
Teacher-rooted trust flood over a BLE RSSI proximity graph, computed server-side.

1. Each phone checks in and gets a random 32-bit ephemeral id for this session. It advertises that id **inside its
   BLE service UUID** (section 2) and scans for everyone else's.
2. Check-in is open 20 s. Every phone keeps discovering 5 s past that (the *discovery tail*), so even the last student to
   tap overlaps everyone for at least 5 s. Then each phone uploads a **signed** list of `(peer, median RSSI, sample count)`
   within 10 s. Total: 25 s of waiting for a student who taps at once (was 45 + 15 s).
3. The server removes the TX/RX imbalance between Android and iOS (**self-calibration**, section 3), then admits an edge
   only when **both** phones heard each other, the two RSSI values agree within `delta_db` (8 dB) and the implied
   distance is within the (density-adaptive) edge threshold.
4. The teacher marks the front bench as verified (seeds). Trust floods from the seeds, bounded by hops (`ttl=8`) and path
   length (`max_path_m=15`). A student is PRESENT only with `k=2` **vertex-disjoint** paths from the seeds
   (Menger / max-flow), so a cluster outside the room cannot vouch for itself through a single doorway phone.
5. Anyone left out is ABSENT; borderline cases are FLAGGED. Optional headcount: if PRESENT exceeds the teacher's count,
   the `gap` lowest-evidence non-seed students are marked `review`.

Why server-side: iOS cannot advertise custom payloads or set TX power, so the flood cannot run phone-to-phone. Phones only
advertise an id and report what they hear, which is identical on iOS and Android.

## 2. On-air format (Android and iOS identical)
One legacy advertisement: flags + one 128-bit service UUID = 21 bytes.

    6e657470-7265-7365-6e63-6500XXXXXXXX      fixed 96-bit NetPresence prefix + 8 hex ephemeral id

* No device name, manufacturer data or scan response, so nothing can be lost to a collision with a scan response,
  and passive scanning still gets the identity. Airtime per advert ~0.3 ms (was ~1 ms with an active-scan exchange).
* Android: `ADVERTISE_MODE_LOW_LATENCY` (~100 ms), `ADVERTISE_TX_POWER_HIGH` (iOS cannot lower its power, so Android
  matches it), hardware scan filter on the prefix with a UUID mask, `SCAN_MODE_LOW_LATENCY`.
* iOS: advertises the UUID only (foreground), scans with `services: nil` + `AllowDuplicates` and matches the prefix in code.
* Both native sides send samples to JS in batches every 200 ms (a full room is ~900 adverts/s; one bridge event per advert
  would stall a mid-range phone). The id rotates every session; Android and iOS also randomise the MAC address.
* Shared constants and a cross-language vector: `mobile/core/src/ble.ts`, `docs/test-vectors.json`.

## 3. Self-calibration (cross-platform)
For a mutual pair, `r_ab = PL + rx_a + tx_b`, `r_ba = PL + rx_b + tx_a`. Shadowing is the same path both ways, so the
difference `r_ab - r_ba = w_A - w_B` with `w = rx - tx` depends only on the two phones' **platforms**. The server solves one
`w` per platform by least squares over every cross-platform pair in the session (one outlier-trimming pass), then shifts
readings by `w/2` so pairs become symmetric while their mean (which sets the distance) is unchanged.

* No lab calibration is needed for the Android/iOS gap. Simulated: 12 dB imbalance -> 35.9% of the class lost without it,
  0.45% with it.
* **Security:** the correction is pooled per platform, never per phone. A phone inflating all its readings by 15 dB moves
  its platform's estimate by 0.03 dB and keeps its lopsided links, which the agreement test still rejects. Platforms with
  fewer than 3 phones in the session are not corrected at all. Platform comes from the enrolled model string
  (`Apple ...` = iOS). Switch off with `AUTOCAL=0`.
* Per-model calibration (`PUT /api/devices/calibration`) still sets each model's link budget (`offset = -(rx + tx)`
  relative to the reference); measure it with two phones of the same model (section 7).

## 4. Trust model
* Device keys: ECDSA P-256 in Secure Enclave / Android Keystore. Enrolment is one-time per student (409 on re-enrol;
  teacher can reset). Optional `ENROL_CODE`: a class code told in person, required to enrol, which stops someone outside
  the class from squatting on roll numbers. Compared in constant time.
* Signed messages (SHA-256, DER signature, base64): `register:{student_id}:{model}`, `checkin:{session_id}:{nonce}`,
  `report:{session_id}:{student_id}:` + compact JSON of rows `[peer, int rssi, int count]` sorted by peer. See
  `docs/test-vectors.json`. Malformed keys or signatures are rejected (400/401), never a server error.
* Teacher endpoints require `X-Teacher-Token` (constant-time compare). Set `TEACHER_TOKEN`; the default logs a warning.
* Residual attack: **collusion**. `k` accomplices inside coverage vouching for an absent friend defeat k-witness
  (simulated: succeeds exactly when accomplices >= k). Mitigations: raise `k`, headcount reconciliation, teacher review.

## 5. API (all under `/api`)
| Method / path | Who | Purpose |
|---|---|---|
| `POST /devices/register` | student | enrol key (proof of possession; `enrol_code` if the server sets one) |
| `GET /devices`, `DELETE /devices/{id}`, `PUT/GET /devices/calibration` | teacher | roster, reset, per-model RSSI offsets |
| `POST /sessions/start` | teacher | open the roll call (optional overrides incl. `k`, `autocal`, `window_seconds`) |
| `GET /sessions/open` | student | current session id, nonce, deadlines, `server_time` |
| `POST /sessions/{id}/checkin` | student | signed; returns `eph_id`, `advertise_uuid`, `window_ends_at`, `discovery_ends_at`, `report_deadline`, `server_time` |
| `POST /sessions/{id}/report` | student | signed neighbour list (<= 200 rows) |
| `POST /sessions/{id}/verify-seeds` | teacher | choose seed students |
| `POST /sessions/{id}/close` | teacher | compute result; optional `headcount` |
| `GET /sessions/{id}/result`, `POST /sessions/{id}/adjudicate` | teacher | results; resolve a review/flag |
| `WS /sessions/ws/{id}?token=` | teacher | live check-ins |
| `/acoustic/*` | both | v1 baseline incl. trial logging for failure characterisation |

## 6. Parameters and results
Defaults in `backend/app/config.py` / `.env.example`. Edge threshold is **density-adaptive** by check-ins:
2.0 m (>= 70), 2.5 m (50-69), 3.0 m (30-49), 3.5 m (< 30).

Simulated (3 bench columns x 8 benches x 4 seats, Android/iOS mix, students tap after a lognormal delay with a 4 s
median). Reproduce everything with `python -m tools.check` (~2.5 min); numbers below are from that run.
* 93 students: 0.4% false-absent (mostly students who tapped after check-in closed), 0% corridor admission with the door
  closed, 0% with it open; across 35-93 students worst 1.2% false-absent and 9.4% corridor admission (door open).
* 20 students: 2.2% false-absent (was 5% under the old radio model, 16.5% with tap delays before the 3.5 m step).
* Any iOS share 0-100%: <= 0.39% false-absent. Pessimistic iPhones (reports coalesced to 30%, advertising every 300 ms):
  0.43%.
* Check-in window at 93 students: 10 s 6.6%, 15 s 1.35%, **20 s 0.36%**, 45 s 0.02% (late tappers dominate).
* TTL >= 6 needed (ttl=4: 10.7% false-absent). Collusion succeeds exactly when accomplices >= k.
* Speed: a 93-student close takes ~30 ms in the engine; one simulated classroom ~70 ms; each study ~50 s on 2 cores.

## 7. Measurement protocols (do these before trusting the numbers)
1. **RSSI calibration.** Use the app's *BLE lab* screen in the actual classroom at 1, 2, 3, 4, 6 m, with **two phones of
   the same model** facing each other (so the fit captures that model's rx + tx). Export CSV (`model,distance_m,rssi`) and
   run `python -m tools.fit_pathloss samples.csv --ref-model "<model>"`. Put A, n into `.env` and offsets into
   `PUT /api/devices/calibration`, then re-run `python -m tools.check`.
2. **Sample rate.** The BLE lab shows samples per peer. The simulator assumes ~10 adverts/s from Android, ~6.7/s from iOS,
   scan efficiency 0.6-0.95. Replace them in `sim/room.py` with what you measure.
3. **Tap timing.** Time how long a real class takes to tap after "everyone mark present now". If the median is well above
   4 s, raise `WINDOW_SECONDS`.
4. **Acoustic baseline.** Use the Acoustic tab's trial mode in the same room to log success/failure by seat and phone.

## 8. Operating notes
Teacher flow: Start -> students tap -> verify front bench -> (optional headcount) -> Close -> review flagged rows.
Students keep the app open for ~25 s (the app keeps the screen awake; iOS only works in the foreground). A student who
taps after check-in closes is told the roll call is closed, and the teacher can start another. Clock skew is corrected
using `server_time`.

## 9. Limitations
* The radio model is assumed, not measured: path-loss exponent, shadowing, body loss, iOS TX power, advertising interval
  and duplicate-report rate. Real classrooms (metal benches, crowds, fans) may shift every threshold.
* The native Android and iOS code has never been compiled or run on a phone here (see `mobile/README.md`); GitHub
  Actions compiles it.
* iOS: foreground only; no custom TX power.
* Collusion and relay attacks are mitigated, not eliminated.
* The in-memory dev database is not persistent; use MongoDB in production. The teacher token is a shared secret, not
  per-user authentication.
