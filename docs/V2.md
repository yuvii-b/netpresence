# NetPresence v2: proximity-graph attendance

## 1. Idea
Teacher-rooted trust flood over a BLE RSSI proximity graph, computed server-side.

1. Each phone advertises a random ephemeral ID (`NP-<8 hex>`, assigned per session at check-in) and scans for others.
2. After the discovery window (45 s) each phone uploads a **signed** list of `(peer, median RSSI, sample count)`.
3. The teacher marks the front bench as verified (seeds). The server admits an edge only when **both** phones heard each
   other, RSSI values agree within `delta_db` (8 dB) and the implied distance is within the edge threshold.
4. Trust floods from the seeds, bounded by hops (`ttl=8`) and path length (`max_path_m=15`). A student is PRESENT only with
   `k=2` **vertex-disjoint** paths from the seeds (Menger / max-flow), so one clustered group outside the room cannot
   vouch for itself through a single doorway phone.
5. Anyone left out is ABSENT; borderline cases are FLAGGED for the teacher. Optional headcount: if PRESENT exceeds the
   teacher's count, the `gap` lowest-evidence non-seed students are marked `review`.

Why server-side: iOS cannot advertise custom payloads or set TX power, so the flood cannot run phone-to-phone. Phones only
advertise an ID and report what they hear, which is identical on iOS and Android.

## 2. Trust model
* Device keys: ECDSA P-256 in Secure Enclave / Android Keystore. Enrolment is one-time per student (409 on re-enrol; teacher can reset).
* Signed messages (SHA-256, DER signature, base64): `register:{student_id}:{model}`, `checkin:{session_id}:{nonce}`,
  `report:{session_id}:{student_id}:` + compact JSON of rows `[peer, int rssi, int count]` sorted by peer. See `docs/test-vectors.json`.
* Teacher endpoints require `X-Teacher-Token`. Set `TEACHER_TOKEN`; the default is insecure and logs a warning.
* Residual attack: **collusion**. `k` accomplices sitting inside coverage and vouching for an absent friend defeat k-witness
  (simulated: succeeds exactly when accomplices >= k). Mitigations: raise `k`, headcount reconciliation, teacher review.

## 3. API (all under `/api`)
| Method / path | Who | Purpose |
|---|---|---|
| `POST /devices/register` | student | enrol key (proof of possession) |
| `GET /devices`, `DELETE /devices/{id}`, `PUT/GET /devices/calibration` | teacher | roster, reset, per-model RSSI offsets |
| `POST /sessions/start` | teacher | open window (optional param overrides) |
| `GET /sessions/open` | student | current session id + nonce |
| `POST /sessions/{id}/checkin` | student | signed; returns `eph_id`, `advertise_name`, `service_uuid`, `window_ends_at`, `report_deadline`, `server_time` |
| `POST /sessions/{id}/report` | student | signed neighbour list |
| `POST /sessions/{id}/verify-seeds` | teacher | choose seed students |
| `POST /sessions/{id}/close` | teacher | compute result; optional `headcount` |
| `GET /sessions/{id}/result`, `POST /sessions/{id}/adjudicate` | teacher | results; resolve a review/flag |
| `WS /sessions/ws/{id}?token=` | teacher | live check-ins |
| `/acoustic/*` | both | v1 baseline incl. trial logging for failure characterisation |

## 4. Parameters
Defaults in `backend/app/config.py` / `.env.example`. The edge threshold is **density-adaptive** unless set per session:
2.0 m for >=70 check-ins, 2.5 m for 50-69, 3.0 m below (sparser rooms need a looser edge to stay connected; dense rooms leak if loose).

## 5. Simulated results (93-student room: 3 columns x 8 benches x 4 seats, door open unless noted)
Assumed radio: `RSSI = -59 - 30 log10(d)` + shadowing, body loss, per-model bias. Run `python -m sim.orientation` to reproduce.
* 93 students: corridor admission ~3.4% door open, 0% door closed; false-absent <=0.8% across 35-93 students.
* 20 students: ~5% false-absent (sparse; known limitation).
* Seed bench in the middle column is best; left/right seeds ~2.7% false-absent at 60 students.
* TTL >= 6 needed (ttl=4 gives 7.8% false-absent). Edge 1.5 m is too tight (22% false-absent); 2.5 m leaks ~5% at 93.
* Collusion succeeds when accomplices >= k.

## 6. Measurement protocols (do these before trusting the numbers)
1. **RSSI calibration.** Use the app's *BLE lab* screen: one phone advertises, another logs at 1, 2, 3, 4, 6 m in the actual
   classroom, several phone models. Export CSV (`model,distance_m,rssi`) and run
   `python -m tools.fit_pathloss samples.csv --ref-model "<model>"`. Put the resulting A, n into `.env` and offsets into
   `PUT /api/devices/calibration`. Re-run the simulation with those values.
2. **Android scan mode.** Confirm on mid-range phones that LOW_LATENCY scanning yields >= 3 samples/peer in 45 s (the BLE sim
   says duty-cycled modes are the main risk).
3. **Acoustic baseline.** Use the Acoustic tab's trial mode in the same room to log success/failure by seat and phone.

## 7. Operating notes
Teacher flow: Start -> students tap -> verify front bench -> (optional headcount) -> Close -> review flagged rows.
Students must keep the app in the foreground for ~45 s (iOS limitation). Clock skew is corrected using `server_time`.

## 8. Limitations
* Radio model is assumed, not measured. Real classrooms (metal benches, crowds, fans) may shift all thresholds.
* Native Android/iOS code is unbuilt and untested on hardware (see `mobile/README.md`).
* iOS: foreground only; iOS-to-iOS discovery needs the app open on both; no custom TX power.
* Collusion and relay attacks are mitigated, not eliminated. Sparse rooms (<~30) have higher false-absent rates.
* No persistence of the in-memory dev DB; use real MongoDB in production. Teacher token is a shared secret, not per-user auth.
